prose, scroll to an infobox value, follow a link and read the next page, type a

## Failures that were bugs in general machinery

Each fix is general (any app, any page), not a task patch.

| symptom on a real page | cause | general fix |
| --- | --- | --- |
| Scrolled Wikipedia pages read as **0 elements** | Off-screen subtree pruning: Safari's web containers keep a screen-sized frame that scrolls away (y=-1189) while children stay visible | Never prune by a parent's frame |
| Answer on screen, extraction said "not observed" | Evidence refused new entries once full, so a long scroll lost its **latest** screens | Evict the least recently seen entries; the current screen always fits |
| Label and value split across nodes ("Height" / "330" / "m (1,083") | Tables, forms and infoboxes link label and value only by visual row | Every evidence entry carries its **row context**, used by selection and verification |
| Fact mid-sentence ("built … from 1887 to 1889.") could not be selected | Selection offered whole labels only | Offer date, number and unit tokens, plus bare numbers inside dates |
| "15 December 1832" chosen for `birth_year`, verifier rejected | Granularity | Selection instructed to match field granularity; a rejected pick gets one generative second opinion under the same contract |
| Typing into Safari's address bar: WDA "stale element" | Focus swaps in a different editing field | TYPE = tap to focus, wait for keyboard, send keys to the focused field |
| Screen change before dispatch ended the run as "outcome unknown" | Pre-dispatch refusal raised as a transport error | Raised as a pre-dispatch rejection: re-observe and decide again |
| Typed a search, then stalled | No way to submit | `SUBMIT` (Return/Go) and `TYPE_SUBMIT` (type + Return) operations, verified and ledgered; a duplicate TYPE is refused with a hint once instead of ending the run |
| Text entry demoted to WAIT for many steps | Adding TYPE_SUBMIT split probability with TYPE below the floor | Confidence floors apply to an operation *family's* combined mass |
| Lazy-loading pages invalidated two decisions per task | Any change anywhere made the pre-dispatch check stale | Plain navigation taps proceed if their own target is identical in the fresh read |
| Tasks failed when a message arrived | WDA picks the foreground app at (64,64), under notification banners; the banner's **message text** entered the observation | Active-app detection point moved to the screen center |
| `SafariWindow?View=…&UUID=…` in screen text | Identifier names used as labels | Identifier-shaped names without a human label are dropped |
| Ada Lovelace page crashed the parser | 4000-node budget during page load | Budget 12000 |

## Honest findings

- The first "how tall" task was **ambiguous** (infobox lists 300 m architectural
  and 330 m tip). The agent split 0.43/0.36 and declined; that is correct
  behaviour. The task was reworded to ask for the height to the tip.
- The answer **verifier is ~50/50 on multi-hop answers** ("open the article
  about the engineer it is named after, report his birth year"): correct
  "1832" was judged supported 0.51–0.56 vs unsupported 0.40–0.53 across runs,
  with evidence ranked by request relevance and the action trail supplied.
  That is a verifier calibration limit, not a plumbing bug; the check was not
  loosened.
- **Chrome** (this phone's default browser) keeps its tab switcher in the
  accessibility tree; the fast read cannot tell it is hidden, and WDA's own
  `visible` attribute hides real web content instead (4 of 78 elements on a
  Safari article). Tasks target Safari explicitly; Chrome is a known gap.
- Search still fails 0/3 with mixed causes (helper budget exhausted by recovery
  hints, a transport error, verifier UNCLEAR on a TYPE_SUBMIT).
